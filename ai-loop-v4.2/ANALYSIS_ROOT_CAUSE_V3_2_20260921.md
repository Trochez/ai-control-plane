# ai-loop v3.2 incident analysis → v4.0 remediation

## Executive conclusion

The recurring failures were not primarily failures to navigate ChatGPT. The browser repeatedly reached useful UI states, including a fresh `New chat in Bot_trading` composer, Chat surface, and High reasoning. The dominant failure was the transport/proof architecture: Python asked an LLM-driven OpenCode CLI turn to call Playwright, then scraped the CLI transcript for a nonce-bound string that was expected to be the Playwright return value. In the observed failures, the transcript contained the *JavaScript source passed to the tool* and tool chatter, but not the returned proof line. The controller therefore reported `ADAPTIVE_PLAYWRIGHT_PROOF_MISSING` even after meaningful browser actions occurred.

The same design also made bootstrap slow: one failed attempt could consume several minutes of model navigation, and v3.2 allowed up to three attempts before declaring failure.

v4.0 removes the LLM/OpenCode transcript from the authoritative browser write path.

## Confirmed findings from the supplied v3.2 log

1. **Fresh project navigation was substantially working.** The screenshot shows an empty composer labelled `New chat in Bot_trading`; the log also shows direct interaction with model, attachment, composer and send controls.
2. **Proof extraction failed after action execution.** `ADAPTIVE_PLAYWRIGHT_PROOF_MISSING` tails contain the literal `playwright_browser_run_code_unsafe` JavaScript and expected return construction, rather than the result generated by that JavaScript.
3. **Model selector assumptions were brittle.** The selector `[role="menuitemradio"][aria-checked="true"]` matched no element even though the UI was usable.
4. **Upload transport was brittle.** `playwright_browser_file_upload` failed because the MCP tool required a related modal state. This is avoidable with Playwright `setInputFiles()` / `filechooser` directly.
5. **The model was allowed to perform too many browser operations before proof.** This produced long tool sequences and made a proof failure difficult to distinguish from an action failure.
6. **Ambiguous-send recovery re-entered the same proof family.** After an uncertain send, `_recover_delivery_via_browser()` could again fail with `ADAPTIVE_PLAYWRIGHT_PROOF_MISSING`, so the recovery mechanism shared the failure mode it was supposed to recover from.
7. **The retry budget amplified latency.** The observed timestamps show roughly 9 minutes to attempt 1, ~6 more to attempt 2 and ~5 more to attempt 3 before failure, despite no verified delivery.

## Root causes

### RC1 — LLM transcript used as a transport for deterministic browser proof

The authoritative parser `_parse_adaptive_payload_line()` searched `opencode run` stdout/stderr for a proof prefix. The LLM was responsible for making a final Playwright tool call whose returned line then had to survive OpenCode CLI rendering. That couples correctness to model behavior and CLI rendering rather than browser state.

### RC2 — Model in the critical create/attach/send path

Bootstrap used an LLM as a UI navigator. This is appropriate for advisory discovery, but not for an idempotent transaction with exact send semantics. A slow or verbose model turn directly delayed the control plane.

### RC3 — UI-specific assumptions mixed with proof logic

Selectors such as `menuitemradio[aria-checked=true]` were treated as necessary proof even though ChatGPT can render equivalent controls using different roles/state attributes.

### RC4 — Send and recovery did not share one physical authority

The sender was model-driven while recovery used a different observer path. Because the sender could click before proof and the observer could fail independently, the controller entered ambiguous states.

## v4.0 architecture

### Direct browser worker

`playwright-bootstrap-worker.cjs` launches the existing dedicated persistent Chrome profile directly with the cached Playwright Node package. No OpenCode model is involved in bootstrap or policy verification.

The worker performs:

1. Navigate to the exact `bot_trading` project root.
2. Prove or create an empty project draft.
3. Ensure normal Chat surface.
4. Select/verify `GPT-5.6 Sol` and `High` using semantic controls with broad role support.
5. Attach the plan using `input[type=file].setInputFiles()` or a real Playwright `filechooser`, eliminating the MCP upload-modal dependency.
6. Fill the exact delivery marker + implementation message.
7. Persist a browser-local ledger as `READY`, then `SENDING` immediately before the only Send click.
8. Click Send once.
9. Prove the marker exists in a user turn and that the URL is persistent `/c/...`.
10. Persist `SENT` and return a plain worker JSON object directly to Python.

### No LLM in any controller send path

`guarded_send()` also uses the direct worker (`SEND_EXISTING`). The LLM can still inspect settled assistant responses and classify actions, but it cannot own typing, attachment or Send.

### Direct policy guard

`ensure_chat_policy()` now calls the direct worker (`POLICY_ONLY`). The repeated `AI_LOOP_BROWSER_OBS_V1` transcript-proof family is no longer authoritative for Chat/Sol/High verification.

### Ambiguous send

If a Send click occurs but the marker cannot be proven, the sender is never retried. Recovery uses `playwright-bootstrap-observer.cjs` directly (Node/Playwright, read-only), not OpenCode/model transcript parsing.

### Diagnostics

Every worker failure writes controller-owned evidence under:

`/var/lib/ai-loop/runs/<RUN_ID>/browser/deterministic-bootstrap/`

or

`/var/lib/ai-loop/runs/<RUN_ID>/browser/deterministic-send/`

including JSON state, full HTML and screenshot when available.

## Performance effect

The initial delivery no longer requires an OpenCode LLM turn. The controller invokes a local Node process that drives Playwright directly. OpenCode capability probing is deferred until *after* the plan has been sent because it is needed for later response/action interpretation, not for bootstrap.

## Scope and guarantees

v4.0 removes the specific architectural family that caused the repeated v3.0-v3.2 failures: model-driven browser mutation + transcript proof extraction. It also removes model ownership from every controller send.

No software can guarantee that a third-party website will never change or that network/authentication failures can never occur. v4.0 instead guarantees these controller properties:

- no blind resend after a click;
- no model-generated proof is authoritative for browser writes;
- no OpenCode CLI transcript is required to prove bootstrap/send success;
- pre-send errors are retryable only before a click;
- post-click ambiguity is read-only recovery only;
- exact delivery marker and browser-local ledger are required;
- fresh project identity, attachment and exact message are verified before Send;
- deterministic diagnostics are persisted on failure.
