# ai-loop v3.2 incident analysis → v4.0 remediation

## Executive conclusion

recurring failures were not primarily failures to navigate ChatGPT. browser repeatedly reached useful UI states, including fresh `New chat in Bot_trading` composer, Chat surface, and High reasoning. dominant failure was transport/proof architecture: Python asked LLM-driven OpenCode CLI turn to call Playwright, then scraped CLI transcript for nonce-bound string that was expected to be Playwright return value. In observed failures, transcript contained *JavaScript source passed to tool* and tool chatter, but not returned proof line. controller therefore reported `ADAPTIVE_PLAYWRIGHT_PROOF_MISSING` even after meaningful browser actions occurred.

same design also made bootstrap slow: one failed attempt could consume several minutes of model navigation, and v3. 2 allowed up to three attempts before declaring failure.

v4. 0 removes LLM/OpenCode transcript from authoritative browser write path.

## Confirmed findings from the supplied v3.2 log

1. **Fresh project navigation was substantially working. ** screenshot shows empty composer labelled `New chat in Bot_trading`; log also shows direct interaction with model, attachment, composer and send controls.
2. **Proof extraction failed after action execution. ** `ADAPTIVE_PLAYWRIGHT_PROOF_MISSING` tails contain literal `playwright_browser_run_code_unsafe` JavaScript and expected return construction, rather than result generated by that JavaScript.
3. **Model selector assumptions were brittle. ** selector `[role="menuitemradio"][aria-checked="true"]` matched no element even though UI was usable.
4. **Upload transport was brittle. ** `playwright_browser_file_upload` failed because MCP tool required related modal state. This is avoidable with Playwright `setInputFiles()` / `filechooser` directly.
5. **model was allowed to perform too many browser operations before proof. ** This produced long tool sequences and made proof failure difficult to distinguish from action failure.
6. **Ambiguous-send recovery re-entered same proof family. ** After uncertain send, `_recover_delivery_via_browser()` could again fail with `ADAPTIVE_PLAYWRIGHT_PROOF_MISSING`, so recovery mechanism shared failure mode it was supposed to recover from.
7. **retry budget amplified latency. ** observed timestamps show roughly 9 minutes to attempt 1, ~6 more to attempt 2 and ~5 more to attempt 3 before failure, despite no verified delivery.

## Root causes

### RC1 — LLM transcript used as a transport for deterministic browser proof

authoritative parser `_parse_adaptive_payload_line()` searched `opencode run` stdout/stderr for proof prefix. LLM was responsible for making final Playwright tool call whose returned line then had to survive OpenCode CLI rendering. That couples correctness to model behavior and CLI rendering rather than browser state.

### RC2 — Model in the critical create/attach/send path

Bootstrap used LLM as UI navigator. This is appropriate for advisory discovery, but not for idempotent transaction with exact send semantics. slow or verbose model turn directly delayed control plane.

### RC3 — UI-specific assumptions mixed with proof logic

Selectors such as `menuitemradio[aria-checked=true]` were treated as necessary proof even though ChatGPT can render equivalent controls using different roles/state attributes.

### RC4 — Send and recovery did not share one physical authority

sender was model-driven while recovery used different observer path. Because sender could click before proof and observer could fail independently, controller entered ambiguous states.

## v4.0 architecture

### Direct browser worker

`playwright-bootstrap-worker.cjs` launches existing dedicated persistent Chrome profile directly with cached Playwright Node package. No OpenCode model is involved in bootstrap or policy verification.

worker performs:

1. Navigate to exact `bot_trading` project root.
2. Prove or create empty project draft.
3. Ensure normal Chat surface.
4. Select/verify `GPT-5.6 Sol` and `High` using semantic controls with broad role support.
5. Attach plan using `input[type=file].setInputFiles()` or real Playwright `filechooser`, eliminating MCP upload-modal dependency.
6. Fill exact delivery marker + implementation message.
7. Persist browser-local ledger as `READY`, then `SENDING` immediately before only Send click.
8. Click Send once.
9. Prove marker exists in user turn and that URL is persistent `/c/...`.
10. Persist `SENT` and return plain worker JSON object directly to Python.

### No LLM in any controller send path

`guarded_send()` also uses direct worker (`SEND_EXISTING`). LLM can still inspect settled assistant responses and classify actions, but it cannot own typing, attachment or Send.

### Direct policy guard

`ensure_chat_policy()` now calls direct worker (`POLICY_ONLY`). repeated `AI_LOOP_BROWSER_OBS_V1` transcript-proof family is no longer authoritative for Chat/Sol/High verification.

### Ambiguous send

If Send click occurs but marker cannot be proven, sender is never retried. Recovery uses `playwright-bootstrap-observer.cjs` directly (Node/Playwright, read-only), not OpenCode/model transcript parsing.

### Diagnostics

Every worker failure writes controller-owned evidence under:

`/var/lib/ai-loop/runs/<RUN_ID>/browser/deterministic-bootstrap/`

or

`/var/lib/ai-loop/runs/<RUN_ID>/browser/deterministic-send/`

including JSON state, full HTML and screenshot when available.

## Performance effect

initial delivery no longer requires OpenCode LLM turn. controller invokes local Node process that drives Playwright directly. OpenCode capability probing is deferred until *after* plan has been sent because it is needed for later response/action interpretation, not for bootstrap.

## Scope and guarantees

v4. 0 removes specific architectural family that caused repeated v3. 0-v3. 2 failures: model-driven browser mutation + transcript proof extraction. It also removes model ownership from every controller send.

No software can guarantee that third-party website will never change or that network/authentication failures can never occur. v4. 0 instead guarantees these controller properties:

- no blind resend after click;
- no model-generated proof is authoritative for browser writes;
- no OpenCode CLI transcript is required to prove bootstrap/send success;
- pre-send errors are retryable only before click;
- post-click ambiguity is read-only recovery only;
- exact delivery marker and browser-local ledger are required;
- fresh project identity, attachment and exact message are verified before Send;
- deterministic diagnostics are persisted on failure.
